# EnvShield Backlog

This is the durable, itemized engineering record: confirmed bugs, security
issues, limitations, feature requests, architectural questions, performance
unknowns, and strategic directions discovered through EnvShield development,
Zeus integration, external user feedback, competitive research, and audits.

**This is not the roadmap.** [ROADMAP.md](ROADMAP.md) is curated public
direction (what ships, what's next, what's explicitly not being built).
This file is the operational ledger behind it — every individual finding,
its evidence, and its status, so nothing gets silently lost or silently
promoted. ROADMAP.md should eventually *reference* major themes from here;
this pass does not rewrite ROADMAP.md.

**Rule zero:** never convert one evidence status into another without
re-stating the evidence. A `NEEDS_EVIDENCE` item becomes `CONFIRMED` only
by recording what was reproduced and how. A `CONFIRMED` item is never
deleted when fixed — it's marked `Decision: Fixed in vX.Y.Z` and kept, so a
regression can never quietly reintroduce something already found once.

## Evidence status legend

| Status | Meaning |
|---|---|
| `CONFIRMED` | Directly reproduced or verified against current source, live or via direct code reading with citation. |
| `NEEDS_EVIDENCE` | Plausible, sourced from a document or inference, not independently verified this pass. |
| `STALE` | Was true in an older version/state; no longer true. |
| `REFUTED` | Tested and found not to be true. Kept, not deleted, so it isn't re-raised. |
| `STRATEGIC` | Product/architecture direction, not a current defect. |
| `USER_FEEDBACK` | External user report/question that may indicate a product requirement. |
| `RESEARCH` | Competitive/market observation. |

## ID scheme

`BL-NNN` is the stable, primary ID going forward. Where a finding was
already named elsewhere (the original Zeus audit's `G-N`, the 2026-08-21
release-readiness audit's `RA-PN-N`, this engagement's own `EB-N`/`G3-N`/
`AD-N`/`FUT-N`), that name is kept alongside as an alias — never orphan a
finding from where it was first discovered.

### BL-001 (aka RA-P0-4) — Secret + `defaultValue` propagates into committed/generated output
Type: `SECURITY` · Evidence: `CONFIRMED` · Priority: **P0**
Source(s): 2026-08-21 release-readiness audit; independently live-reproduced this engagement's own verification pass.
Component: `schema_types.py` (shared `secret_default_conflict` predicate), `config/manager.py` (schema-load-time rejection — the fix's primary gate), `schema_manager.py` (`schema sync`'s `.env.example` body, `check`'s `_source_label`), `generator.py` (Python/TypeScript codegen), `explain.py` (`_describe_field`)

- **Problem:** A schema field with `secret = true` and a real `defaultValue` was accepted with no rejection anywhere.
- **Current behavior (fixed 2026-08-26):** Previously the value was written verbatim into `.env.example` (`schema sync`), into generated Python (`pydantic-settings` field default), and into generated TypeScript (`z.string().default(...)`, embedded in the literal before the `Secret<T>` wrapper is even applied at export). While tracing every consumer of a field's `defaultValue` for this fix, two further, previously-undiscovered manifestations of the same root cause were found and fixed in the same pass: `envshield explain`'s field description (`explain.py::_describe_field`, both Rich and `--json`) and `check`'s "Missing in Local"/"Blank in Local" Rich table (`schema_manager.py::_source_label`) both also echoed a secret field's real default with no check against the `secret` flag.
- **Root cause:** No code path anywhere consulted the `secret` flag before echoing `defaultValue`. The five manifestations above shared one implementation boundary that made a single fix possible: every schema-consuming command (`check`/`doctor`/`setup`/`schema sync`/`generate`/`explain`/`scan`) already loads its schema through exactly two entry points, `config_manager.load_schema`/`load_bare_schema` → `_load_schema_file`.
- **Fix:** Two-layer defense-in-depth, no new abstraction — both layers reuse a single new pure predicate, `schema_types.secret_default_conflict(field_schema)` (mirrors an invariant `importer.py`'s schema *generation* already enforced unconditionally: a variable classified secret never got a `defaultValue` in the first place).
  1. **Primary gate:** `config_manager.load_schema`/`load_bare_schema` now call `_reject_secret_defaults` immediately after resolving the schema (post-`extends`-merge), raising a new `SecretDefaultConflictError` naming the offending field(s) — never the value itself — if any field is `secret` with a non-empty `defaultValue`. This closes all five manifestations (and any future one) for every real command in one place, the same way an unsafe schema key name is already rejected outright rather than left for each generator to notice.
  2. **Defense in depth:** each of the five original render sites also independently treats a secret field's conflicting default as absent (masks/omits it) via the same predicate, so a schema dict that reaches `generate_config`/`sync_schema`/`_source_label`/`_describe_field` directly (bypassing the loader — which is exactly how the existing test suite's own `mocker.patch("envshield.config.manager.load_schema", return_value=...)` pattern works) still can't leak.
  - **Explicitly out of scope, by design:** the *local* Python secrets file (`_sync_python_local_file` / `setup_manager._fill_schema_defaults`) — that file is the intended destination for a real secret value (created via `file_updater.open_new_secret_file`, 0600 permissions, not committed), so a secret's `defaultValue` seeding it is correct behavior, not a leak. `schema_snapshot.py`'s explicit-revision path (`schema diff` against a historical Git revision, via `git show`) is also untouched — it must still be able to represent a past, possibly-broken schema state for comparison; only the live-working-tree path (`revision=None`, which already delegates to `config_manager.load_schema`) is gated.
- **Evidence/reproduction:** Original bug live-reproduced with a synthetic marker (`SYNTHETIC_NOT_A_SECRET_123` / a fake value) across all three originally-reported outputs in an isolated `/tmp` project. Fix independently live-reproduced 2026-08-26 against the real `envshield` console script (not just `pytest`) in a fresh isolated `/tmp` project with a `sk_live_SYNTHETIC_NOT_A_REAL_SECRET` marker: `check`/`schema sync`/`generate --lang python`/`generate --lang typescript`/`explain` all now refuse to load with a clear, non-leaking `SecretDefaultConflictError` and exit 1; after removing the conflicting default, all five commands succeed, `grep -r` for the marker across every generated artifact (`.env.example`, `config.py`, `config.ts`) found nothing, the field renders correctly as required (`...`/`z.string().min(1)`) and still typed `SecretStr`/`Secret<T>`, and a sibling non-secret default (`LOG_LEVEL=info`) was confirmed completely unaffected in all outputs.
- **Impact:** `.env.example` and generated config modules are exactly the files EnvShield's own workflow instructs a user to commit; `explain --json` and `check`'s terminal output are exactly the surfaces the charter's §4 invariants name directly ("never expose secret values in normal output," "...in JSON"). Directly violated the charter's own §4 invariant ("never store secret values in the configuration contract").
- **Dependencies:** None.
- **Related:** BL-070 (the DEV.to comment that first raised the conceptual question this bug concretely answers).
- **Tests:** Regression coverage added for the shared predicate (`test_schema_types.py::TestSecretDefaultConflict`, 6 cases including non-string TOML defaults and the empty-string non-conflict edge case), the primary load-time gate (`test_config_manager.py::TestLoadSchemaRejectsSecretDefaults`, 6 cases including an `extends`-inherited conflict and two non-secret/no-conflict sanity checks), and each of the five defense-in-depth render sites (`test_generator.py` ×2 — Python and TypeScript, `test_schema_manager.py` ×2 — `.env.example` sync and `_source_label`, `test_explain.py` ×1). Two pre-existing tests were found to lock in the old (buggy) behavior as their expected result and were corrected rather than left failing: `test_generator.py::test_generate_config_secret_with_default_stays_secret_str` previously asserted the literal secret default appeared in generated Python; `test_setup_manager.py::test_setup_requiredif_explanation_never_leaks_a_secret_triggers_value` and `test_cli.py::test_init_force_preserves_a_hand_corrected_secret_classification` both constructed now-invalid fixture schemas (a secret field with an unrelated defaultValue in the first; an unscoped string-replace that marked three importer-generated fields secret while leaving their inferred defaults in place in the second) — both fixture schemas were narrowed to no longer create the conflict, without weakening either test's actual assertion. Full suite: 979/979 passing. `ruff check .`: clean.
- **Decision:** **Fixed 2026-08-26.** Kept here, not removed, as the record of what was found and fixed — per the charter's own rule that a `CONFIRMED` finding is marked `Decision: Fixed in vX.Y.Z` and kept, never deleted, so a regression can't quietly reintroduce this.
- **Target:** Done. **Released in `v4.6.1`** (2026-08-30), verified against a clean `pip install envshield==4.6.1`. The original wording here — "not yet released ... `v4.6.0` tagged but not live on PyPI" — was doubly wrong and is corrected rather than deleted: `v4.6.0` *was* live on PyPI by then (see `BL-091`), and this fix has since shipped.
- **Notes:** This directly contradicted CLAUDE.md's own summary of the 2026-08-21 audit ("no secret leakage... findings"). **Resolved 2026-08-26 (documentation):** CLAUDE.md §19 (and its AGENTS.md counterpart) corrected to state this and the other three Part 0 blockers explicitly, rather than claiming none exist. **Resolved 2026-08-26 (code):** the bug itself, and the two additional manifestations discovered while fixing it, are fixed per above — this is the first of the four Part 0 blockers to move from "documented as open" to actually closed.

### BL-002 (aka RA-P1-4) — Malformed Python config breaks the `--json` contract and can produce a false clean
Type: `RELIABILITY` · Evidence: `CONFIRMED` · Priority: **P0**
Source(s): 2026-08-21 audit; independently live-reproduced; re-investigated and re-reproduced 2026-08-26 (implementation not yet done — see Decision).
Component: `parsers/_python.py` (`PythonParser.get_vars`), surfaced through `check`/`check --json` and `doctor`/`doctor --json`; also reachable, with different consequences, through `setup`, `schema sync`, `explain`, `service_discovery`, and `import` — see "Affected callers" below.

- **Problem:** `PythonParser.get_vars()` catches `SyntaxError`/`TypeError` internally, `print()`s a warning to stdout, and returns an empty result rather than raising.
- **Current behavior:** `check --json` prints the warning line *before* the JSON document (stdout is not valid single-document JSON); with an empty schema (or a schema where every field has a default), the command exits 0 with `"success": true`. The same warning-before-JSON break also reproduces in `doctor --json` — a second command, not named in the original report.
- **Expected behavior:** A parse failure becomes a structured command error; stdout remains exactly one JSON document; exit code is non-zero regardless of schema shape.
- **Evidence/reproduction (2026-08-21, and re-confirmed 2026-08-26 against current `main`, unchanged since first reported):** Live-reproduced with an unterminated-string `.py` fixture via the real `envshield` console script (not just source reading): with an empty schema, `check --json` returns `"success": true, "clean": true` (exit 0) despite the local file being unparseable — the false-clean, reproduced exactly. With any schema that has at least one field without a matching value (required, or defaulted — `should_be_present` still requires a defaulted field's presence), the field correctly shows as `missing` and `success`/`clean` are `false` (exit 1) — no false-clean in that case. In every case, stdout is corrupted: the `Warning: Could not parse...` line prints before the JSON document (confirmed on real stdout, not stderr, via redirection), so `json.loads(stdout)` always raises `JSONDecodeError` regardless of schema shape. `doctor --json` reproduces the identical stdout corruption.
- **Root cause:** `PythonParser.get_vars` is the only parser in `envshield/parsers/` that converts a parse failure into a silent empty result instead of raising. `DockerComposeParser.get_vars` (`_docker_compose.py`) already does the correct thing for the equivalent case — catches `yaml.YAMLError` and raises `EnvShieldException` with a descriptive message — and every caller of `get_vars` across the codebase is already written expecting that contract (see below). This is a single, local inconsistency, not a design gap needing new architecture: the fix is to make `PythonParser.get_vars` match its sibling's existing, already-correct pattern.
- **Affected callers, traced exhaustively (`grep -rn "\.get_vars("`), and how each currently behaves once `PythonParser` raises `EnvShieldException` instead of swallowing:**
  - **Already correct, no change needed** — each already has an `except (..., EnvShieldException, ...)` clause at the point that matters, or the call sits inside a function whose CLI command already wraps the whole body in `except EnvShieldException`: `schema_manager.check_schema`/`check_result` (`schema_manager.py:247,340` — both already have `except (ValueError, EnvShieldException) as e:`), `doctor._check_local_env_sync`/`_check_deployment_manifest` (`doctor.py:100,139` — already handle `EnvShieldException`, and `HealthCheck.run()` itself also catches `EnvShieldException` around every check function as a second layer), `setup_manager._read_seed_values`/`_write_local_env_file` (`setup_manager.py:127,418` — no local catch, but every CLI entry point that reaches `run_setup` — `setup`, `init` — already wraps the call in `except EnvShieldException`), `schema_manager._sync_python_local_file` (`schema_manager.py:558` — same: `sync_schema`'s CLI callers in `schema sync`, `init`, and `import` already wrap it).
  - **Needs a companion one-line fix, or the exception regresses an existing "skip and continue" behavior into an unwanted hard failure:** three call sites currently catch a narrower exception tuple that doesn't include `EnvShieldException`, for code that's deliberately scanning *multiple candidate files* and expects one bad file to be skipped, not to abort the whole operation:
    - `service_discovery.py:146` (`_looks_like_python_config_module`, `except (FileNotFoundError, OSError): return False`) — heuristic discovery over arbitrary directory contents during `init`/`import`.
    - `doctor.py:239` (`_check_config_source_drift`'s inner loop, `except (FileNotFoundError, OSError): continue`) — scans every "other config source" found in a service directory; a malformed one should be skipped, not blank out the whole health check via `HealthCheck.run()`'s coarser outer catch.
    - `importer.py:386` (`merge_variables_from_other_sources`, `except (FileNotFoundError, OSError): continue`) — same shape, during `import`.
    - `explain.py:143` (`_check_manifest_references`, `except (FileNotFoundError, OSError, ValueError) as e:`) — turns a parse failure into a structured per-manifest `status="error"` entry in the report; without `EnvShieldException` added, that specific manifest's failure would instead propagate out of `explain` entirely rather than showing up as one reported entry among others.
  - All four are low-likelihood in practice (a `.py` file would have to be registered as a deployment manifest, or exist as an "other source" the heuristics scan), but each is a genuine, mechanical regression risk directly created by fixing the root cause, so the fix isn't complete without them.
- **Related, adjacent gaps found in the same investigation (not the same defect, not fixed, recorded separately — see BL-092 and BL-093):** `PythonParser.get_vars` also crashes with an *uncaught* `UnicodeDecodeError` on a non-UTF-8/binary `.py` file (`BL-092`); `KubernetesParser.get_vars` has no `try`/`except` around its own YAML parse at all, unlike `DockerComposeParser` (`BL-093`, lower confidence — not fully live-reproduced end-to-end this pass).
- **Existing test coverage gap:** `envshield/tests/parsers/test_python_parser.py::test_python_parser_sad_path_syntax_error` currently asserts the *buggy* behavior as correct (`variables == set()` on a syntax error, docstring calling it "gracefully" handled) — this test will need to be rewritten to assert `EnvShieldException` is raised, the same pattern as `BL-001`'s `test_generate_config_secret_with_default_stays_secret_str`. No existing test exercises `check --json`/`doctor --json`'s stdout-corruption or false-clean behavior at all.
- **Security check:** `str(SyntaxError)` was confirmed (via direct Python testing) to never include the offending source line's actual text — only the error description, filename, and line number; the line's real content lives in a separate `.text` attribute that `str()` doesn't surface. The current warning message, and any fix that continues using `str(e)`, is therefore already safe from leaking a secret value that happened to sit on the malformed line — this must stay true in the fix (use `str(e)` only, never `e.text`).
- **Proposed fix (smallest safe change, no new abstraction):** In `PythonParser.get_vars`, replace the `print(...); return {} if get_values else set()` branch with `raise EnvShieldException(f"Could not parse '{file_path}': {e}")`, mirroring `DockerComposeParser.get_vars`'s existing message shape exactly. Add `EnvShieldException` to the four call sites' except clauses listed above, preserving their existing skip/report semantics. `check_schema`/`check_result`/`doctor`'s health checks/`setup`/`schema sync` need zero changes — they already do the right thing once the exception exists.
- **Impact:** Breaks the documented machine-readable contract for any CI/tooling consumer; can silently report "clean" when the local config literally cannot be read.
- **Dependencies:** None. Distinct from BL-031 (G3-9), which is the same root cause in G-3's *new, unimplemented* union code — fixing this doesn't fix that, and vice versa.
- **Related:** BL-031, BL-092, BL-093.
- **Implementation (2026-08-26):** `PythonParser.get_vars` (`parsers/_python.py`) now raises `EnvShieldException(f"Could not parse '{file_path}': {e}")` instead of `print()`-ing a warning and returning an empty result — exactly the proposed fix above, mirroring `DockerComposeParser.get_vars`'s existing pattern verbatim. `check_schema`/`check_result`/`doctor`'s health checks/`setup`/`schema sync` needed **zero changes**, confirming the investigation's own prediction. Four companion call sites had `EnvShieldException` added to their except clauses to preserve their existing skip-and-continue semantics: `service_discovery.py::_looks_like_python_config_module`, `doctor.py::_check_config_source_drift`'s inner loop, `importer.py::merge_variables_from_other_sources`, `explain.py::_manifest_references`.
- **Tests:** `test_python_parser.py`'s stale sad-path test rewritten to assert the raise (plus a dedicated test proving the message never echoes a secret-shaped value from the malformed line, and a `TypeError`-branch test). New CLI-level regression tests (`test_cli.py`) proving `check --json`/`doctor --json` stdout is valid single-document JSON on a malformed local `.py` file, and that an empty schema no longer false-cleans. A unit-level `check_result` test (`test_schema_manager.py`). Skip-and-continue regression tests at all four companion sites (`test_service_discovery.py`, `test_doctor.py` — via a mocked discovery step, since the normal path already pre-filters a malformed candidate before doctor's own loop would see it — `test_importer.py`, `test_explain.py`). Full suite: 990/990 passing. `ruff check .`: clean.
- **Live verification (2026-08-26):** Reproduced against the real `envshield` console script in an isolated `/tmp` project, mirroring the original investigation's exact scenario: `check --json`/`doctor --json` with an empty schema and an unterminated-string local `.py` file now return `"success": false`/`"clean": false`, exit 1, and `json.loads(stdout)` succeeds — the false-clean and the stdout corruption are both closed. The Rich (non-`--json`) path prints a clean `Error: Could not parse '...'` line, not a raw traceback. A valid `.py` local file continues to check cleanly, unaffected.
- **Decision:** **Fixed 2026-08-26.** Kept here, not removed, per the charter's own rule that a `CONFIRMED` finding is marked `Decision: Fixed in vX.Y.Z` and kept, so a regression can't quietly reintroduce this.
- **Target:** Done. **Released in `v4.6.1`** (2026-08-30) — see CLAUDE.md/AGENTS.md §19 and BACKLOG.md's Part 0 status line.

### BL-092 — `PythonParser.get_vars` crashes uncaught on a non-UTF-8/binary `.py` file
Type: `RELIABILITY` · Evidence: `CONFIRMED` · Priority: **P2**
Source(s): Discovered this pass while investigating `BL-002`'s root cause — a different gap in the same function, not the same defect.
Component: `parsers/_python.py` (`PythonParser.get_vars`)

- **Problem:** `get_vars` opens the file in text mode and calls `f.read()` *inside* its `try: ... except (SyntaxError, TypeError):` block, but `f.read()` can itself raise `UnicodeDecodeError` (a `ValueError` subclass) on invalid-UTF-8 or binary content — a type the except clause doesn't catch.
- **Current behavior:** Live-reproduced directly against `PythonParser`: a `.py` file containing raw non-UTF-8 bytes (`b"\xff\xfe\x00\x01SECRET=1"`) raises an *uncaught* `UnicodeDecodeError` out of `get_vars`. Whether this reaches a user as a raw traceback or a clean CLI error depends entirely on whether the calling command happens to wrap its own call in a broad-enough `except` — the same case-by-case inconsistency `BL-002` is about, just for a different exception type.
- **Expected behavior:** Should raise `EnvShieldException` (or be silently skip-able, for the "opportunistic scan" call sites `BL-002` also identifies), the same as any other unreadable-file case, not propagate as a bare `UnicodeDecodeError`.
- **Evidence/reproduction:** Live-reproduced by calling `PythonParser().get_vars()` directly on a synthetic binary fixture — `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0: invalid start byte`, uncaught.
- **Impact:** Low-likelihood (requires a genuinely binary/corrupted `.py` file where one is expected), but a real, reproducible crash path distinct from `BL-002`'s false-clean/stdout-corruption symptom.
- **Dependencies:** Same component and likely the same fix window as `BL-002` — whoever implements `BL-002`'s fix should decide whether to widen the except clause to also cover this in the same change, since the mechanism (raise `EnvShieldException` instead of swallowing/crashing) is identical.
- **Related:** BL-002.
- **Implementation (2026-08-26):** Bundled into the same change as `BL-002` — `PythonParser.get_vars`'s except clause widened to `(SyntaxError, TypeError, UnicodeDecodeError)`, all three raising `EnvShieldException(f"Could not parse '{file_path}': {e}")`. `str(UnicodeDecodeError)` describes the failing byte's value/position only (confirmed: `'utf-8' codec can't decode byte 0xff in position 0: invalid start byte`), never any decoded text, so this stays consistent with `BL-002`'s security-check note.
- **Tests:** `test_python_parser.py::test_python_parser_non_utf8_content_raises_instead_of_crashing_uncaught` — a real binary fixture on disk (not mocked, since the failure happens in the actual text-mode read), asserting `EnvShieldException` instead of an uncaught `UnicodeDecodeError`.
- **Live verification (2026-08-26):** Reproduced against the real `envshield` console script: a binary local `.py` file now produces a clean `"error": "Could not parse '...': 'utf-8' codec can't decode byte 0xff..."` in both `check --json` and the Rich path, exit 1 — no uncaught traceback.
- **Decision:** **Fixed 2026-08-26.** Kept here, not removed, per the charter's rule that a `CONFIRMED` finding stays recorded once fixed.
- **Target:** Done. **Released in `v4.6.1`** (2026-08-30) — see BACKLOG.md's Part 0 status line (this is a P2, not a Part 0 release blocker itself, but shipped in the same commit as `BL-002`).

### BL-093 — `KubernetesParser.get_vars` has no error handling around its own YAML parse
Type: `RELIABILITY` · Evidence: `NEEDS_EVIDENCE` (confirmed by direct source reading; not fully live-reproduced end-to-end this pass — an attempted live reproduction through `doctor --json` against a malformed Kubernetes manifest did not exercise this code path, for reasons not yet diagnosed) · Priority: **P3**
Source(s): Discovered this pass while comparing `PythonParser`'s error handling against its sibling parsers during `BL-002`'s investigation.
Component: `parsers/_kubernetes.py` (`KubernetesParser.get_vars`)

- **Problem:** Unlike `DockerComposeParser.get_vars`, which wraps `yaml.safe_load` in `try: ... except yaml.YAMLError: raise EnvShieldException(...)`, `KubernetesParser.get_vars` calls `yaml.safe_load_all(f)` with no `try`/`except` around it at all.
- **Current behavior (per source reading only):** A malformed Kubernetes manifest should raise a raw, uncaught `yaml.YAMLError` out of `get_vars`, rather than either `DockerComposeParser`'s friendly `EnvShieldException` or any graceful handling.
- **Expected behavior:** Should match `DockerComposeParser`'s pattern — catch `yaml.YAMLError` and raise `EnvShieldException` with a descriptive message.
- **Evidence/reproduction:** Not yet live-reproduced — an attempt to trigger this through `doctor --json` against a malformed `deployment.yaml` registered in `envshield.yml`'s top-level `manifests:` list did not exercise the "Deployment Manifest" health check at all (the check didn't appear in the `--json` output), suggesting either a manifest-registration or `detect_deployment_format` step short-circuits before reaching `KubernetesParser.get_vars` in that scenario — not yet diagnosed. The source-level gap (no `try`/`except` where `DockerComposeParser` has one) is real and directly confirmed by reading both files side by side.
- **Impact:** Unknown until live-reproduced — could range from "an uncaught traceback on a malformed Kubernetes manifest" (if reachable) to "dead code path, unreachable in practice" (if something upstream always catches malformed YAML first).
- **Dependencies:** None identified yet.
- **Related:** BL-002 (same general theme: parser error-handling consistency; `BL-002` and `BL-092` — the sibling gaps found in the same investigation — were both fixed 2026-08-26, this one was deliberately left open and unimplemented per explicit instruction), BL-003/BL-004's sibling deployment-parser work.

### BL-003 (aka RA-P1-6) — Generated TypeScript boolean coercion inverts `"false"`
Type: `GENERATION` (bug) · Evidence: `CONFIRMED` · Priority: **P0** (scoped to `generate --lang typescript`)
Source(s): 2026-08-21 audit; independently live-reproduced with actual runtime execution, not just source reading.
Component: `generator.py:275` (TypeScript `bool` field rendering)

- **Problem:** `bool` fields render as `z.coerce.boolean()`, which follows JavaScript truthiness.
- **Current behavior:** `z.coerce.boolean().parse("false")` returns `true` at runtime. Confirmed by actually running the generated Zod code (`node` + real `zod` package), not just reading the source — every non-empty string, including `"false"` and `"0"`, coerces to `true`; only `""` coerces to `false`.
- **Expected behavior:** Agrees with EnvShield's own validator, which accepts only case-insensitive `"true"`/`"false"`.
- **Evidence/reproduction:** `node runtime_check.mjs` against real `zod`: `"false" -> true`, `"true" -> true`, `"0" -> true`, `"1" -> true`, `"" -> false`, `"no" -> true`, `"False" -> true`.
- **Impact:** Any boolean-typed environment variable explicitly set to `"false"` (a completely ordinary way to disable a flag — e.g. a safety switch like `ALLOW_EMAILS=false`) resolves to `true` in code generated by EnvShield itself. This inverts explicit developer intent, not just a validation miss. It also directly contradicts README's own marketing claim ("typed, **validated** config code") for this field type — validation exists, it just validates to the wrong value.
- **Investigation (2026-08-26):** Independently re-reproduced this pass (`npm install zod` in an isolated scratch directory, real `node` execution against `generator._zod_base_type`'s exact output) — identical results to the original report (`"false"`/`"0"`/`"no"`/`"False"`/`"FALSE"` all -> `true`; only `""` -> `false`). Root cause confirmed unchanged: `generator.py`'s `_zod_base_type` (line 283-284) emits `z.coerce.boolean()` for every `bool` field, which is JS `Boolean(string)` truthiness, not a `"true"`/`"false"` parse. This is an isolated code path — only `_zod_base_type`'s `bool` branch is affected; the Python side (`_python_type_and_extras`'s `bool` branch emits plain `bool`, validated by pydantic's own strict bool coercion, not affected) and TypeScript's own `enum`/`url`/`email` branches use different, unaffected zod builders. Smallest safe fix: replace the `bool` branch with an explicit case-insensitive `"true"`/`"false"` parser (e.g. a `z.string().transform()` or lowercase-then-`z.enum(["true","false"])` pipeline) that rejects anything else, matching `schema_types._BOOL_VALUES`/`validate_value`'s existing case-insensitive `{"true","false"}`-only contract — no new abstraction needed, this is a one-function, ~5-line change. **Testing-infrastructure gap found:** the existing TypeScript generator tests (`test_generator.py`) exercise real `node` for syntax/injection checks but deliberately *never* import `zod` ("without needing zod or any other module installed" — see `_node_check`'s docstring), and the repo has no root `package.json`/`npm`-dependency setup or `node`/`npm` install step in `.github/workflows/ci.yml` at all (bare `node` is simply assumed present on the runner, an existing assumption this finding doesn't introduce). A regression test that actually proves the *fixed* runtime behavior (not just asserts the generated source string) needs real `zod`, which is a genuine test-infrastructure decision — add `zod` as a scoped devDependency plus an `npm ci`/install CI step, or accept a self-contained hand-written re-implementation of the replacement parser's logic in the test (weaker: can't catch a future zod-behavior drift) — not a decision to make silently inside a "smallest fix" pass.
- **Related:** `BL-094` (new, this pass) — the same generator's `int`/`float`/`port` fields also use `z.coerce.number()`, which independently reproduces as diverging from EnvShield's own validator (accepts `"0x10"`, whitespace-padded, and empty-string-as-`0`) — a related but lower-severity manifestation of the same "no single canonical parsing spec shared by the CLI validator and both codegens" architectural gap. Kept separate: unlike `bool`, none of these inputs silently *invert* declared intent, so it doesn't share BL-003's P0 severity or its narrow scope.
- **Dependencies:** None on `BL-004` — different module (`generator.py` vs `scanner.py`), independent code paths, safe to implement in either order or in parallel.
- **Implementation (2026-08-26):** `generator.py::_zod_base_type`'s `bool` branch (was line 283-284) now returns `z.string().transform((s) => s.toLowerCase()).pipe(z.enum(["true", "false"])).transform((s) => s === "true")` instead of `z.coerce.boolean()`. This accepts only a case-insensitive `"true"`/`"false"` (matching `schema_types._BOOL_VALUES`/`validate_value` exactly) and rejects everything else — including non-string input (`undefined`, `null`, a number, a real boolean) — via zod's own type/enum validation, rather than silently coercing. No new file, no new class, no shared helper — the fix is fully localized to this one branch, exactly as scoped. `_zod_default_literal`'s `bool` branch (already emitting a lowercase `true`/`false` JS literal) needed no change, since the new schema's output type is still a plain boolean. The Python codegen (`_python_type_and_extras`'s `bool` branch, pydantic's own strict bool coercion) was not touched — it was already correct and unaffected by this bug.
- **Tests:** `tests/core/test_generator.py`'s `test_generate_typescript_infers_types_from_default_values` (previously asserted the exact buggy `z.coerce.boolean().default(true)` string as "expected" — corrected to assert the new expression). All behavioral tests execute the actual generated expression text through real, bare `node` (already an unconditional test dependency — see `_node_check`) against a small, faithful hand-written stand-in for the exact 5 zod methods used (`z.string`, `z.enum`, `.transform`, `.pipe`, `.default`, `.optional`) — not a general zod reimplementation and not a substitute for real-package verification, documented as such directly in the test file.
- **Runtime-verification infrastructure decision (per explicit instruction, not made silently):** proving the fix against the *real* `zod` npm package would require adding `package.json`/npm dependency management and a `node`/`npm` CI setup step, none of which exist in this repo today (Python-only tooling throughout). That infrastructure was not added. Real-zod verification was instead performed ad hoc, outside the repository, in an isolated scratch directory (`npm install zod`, real `node`, the actual current `_zod_base_type` output) — see Live verification below — and is not part of the committed, CI-run test suite.
- **Live verification (2026-08-26):** Ran the actual `generator.generate_config()` TypeScript output for a `bool` field end-to-end through real `node` + real `zod` (v4.4.3, via an isolated ad hoc `npm install zod`, not committed to the repo): `ALLOW_EMAILS=false` — the exact scenario named in Impact above — now resolves to `false` (previously `true`). Full matrix against the real package: `"true"`/`"True"`/`"TrUe"` -> `true`; `"false"`/`"FALSE"` -> `false`; `"0"`/`"1"`/`""`/`"no"`/`"yes"`/`" true"`/`"true "`/`undefined`/`null`/`123`/`true` (a real boolean) -> all rejected. Also ran the full local test suite (997 passed, up from 990 — the 7 new tests) and `ruff check .` (clean).
- **Decision:** **Fixed 2026-08-26, committed** (commit `f478f9f`). Independently re-verified against the current working tree in a post-commit verification pass (same day): the generated `bool` expression re-extracted from live `generator.generate_config()` output and re-run against real `node` + real `zod` produced the identical correct matrix (`"false"` -> `false`, case variants accepted, everything else rejected) -- not merely re-reading the diff.
- **Follow-up regression, found and fixed 2026-08-30 at the pre-release gate (`BL-107`):** the fix above appended `.default(false)` to the *end* of the new bool chain. zod 4 returns a default untouched, but **zod 3's `ZodDefault` re-parses it through the inner schema** — feeding a boolean into the chain's leading `z.string()`. ### BL-004 (aka RA-P1-7) — `scan`/`scan --staged` fail open on files over 1MB
Type: `SECURITY` · Evidence: `CONFIRMED` · Priority: **P0**
Source(s): 2026-08-21 audit; independently live-reproduced.
Component: `scanner.py` (large-file skip logic)

- **Problem:** Files >1MB are skipped and recorded in `skipped_files`, but do not affect `clean`.
- **Current behavior:** Both `scan --json` and `scan --staged --json` (the exact mode a pre-commit hook or CI gate uses) report `"clean": true` and exit 0 when the only file containing a secret-shaped marker was the one skipped.
- **Expected behavior:** A skipped file should produce a distinct "incomplete" state and a non-zero exit by default in staged/CI contexts.
- **Evidence/reproduction:** Live-reproduced with a synthetic 1.1MB file containing `AWS_SECRET_ACCESS_KEY=SYNTHETIC0000FAKEKEYNOTAREALSECRET1234` on its first line — both `scan` and `scan --staged` returned `clean: true`, exit 0, with the file correctly named in `skipped_files` but that fact having no effect on the pass/fail verdict.
- **Impact:** Any hook/CI gate that checks only the exit code (the standard integration pattern) is fully bypassed by padding a secret-bearing file past 1MB. This is a bypass of the one feature whose entire job is catching this. **Not hypothetical** — confirmed this pass that EnvShield's own installed pre-commit hook (`scanner.py::_generate_pre_commit_hook_content`) is itself exactly this victim: the generated hook script is `envshield scan --staged` followed by `STATUS=$?` / `exit $STATUS`, i.e. the literal exit-code-only pattern this finding describes, wired in by EnvShield's own `hook install` command.
- **Investigation (2026-08-26):** Independently re-reproduced this pass end-to-end (`envshield scan --json`, `--staged --json`, and plain `--staged` against a live 1MB+ synthetic secret file) — identical to the original report: `clean: true`/exit 0 in all three invocations, file correctly named in `skipped_files`/the printed warning, with no effect on the pass/fail verdict. Root cause confirmed unchanged and precisely localized: `scanner.py::scan_result`'s `"clean": not (secrets or undeclared)` (does not reference `skipped`) and `scanner.py::run_scan`'s `found_issues` (only set from `all_secret_findings`/`all_undeclared_findings`) both omit `skipped_large_files` from the pass/fail computation entirely — this was never a computed-then-discarded value, coverage completeness was simply never wired into either presentation's contract. Both `_scan_files`'s two callers (`run_scan`'s Rich path, `scan_result`'s JSON path) share the one root list, so this is a single shared-computation fix, not two.
  **A required fix-scope dependency, found live-reproducing this:** `_scan_files`'s staged-mode branch runs the >1MB size check (line 669) *before* consulting `excluded_files` (computed from `secret_scanning.exclude_files`/`--exclude`), while the non-staged branch already filters exclusions first via `_filter_files` (line 641) and never reaches the size check for an excluded file at all. Live-reproduced this asymmetry directly: a `secret_scanning.exclude_files: ["*.bin"]`-excluded 1MB+ file is correctly absent from `skipped_files` under plain `scan --json .`, but still lands in `skipped_files` under `scan --staged --json` on the identical file/config. This is harmless today only because a skip has no effect on `clean` — the moment BL-004 is fixed to make any skip flip the pass/fail verdict, this ordering gap becomes an immediate new false-failure source for anyone already using `exclude_files`/`--exclude` on a large, deliberately-out-of-scope file in a staged commit. Fixing BL-004 correctly requires reordering the staged-mode check (consult `excluded_files` before the size check, matching the non-staged branch's existing order) as part of the same change — not a separate backlog item, since implementing BL-004 without it introduces a new regression on day one.
  **Design note carried into the fix, not resolved here:** the recorded "Expected behavior" already anticipates a *distinct* incomplete/unknown state, not simply folding `skipped` into `clean` — e.g. `"clean": not (secrets or undeclared)` staying as-is plus a new `"incomplete": bool(skipped)` field, with the CLI wrapper (`cli.py::scan`, the exact site that currently does `if not result["clean"]: raise typer.Exit(code=1)`) checking both. Whether *every* mode (plain interactive `scan`, not just `--staged`/`--json`) should also flip exit code on a skip, or only the hook/CI-facing invocations, is a real product/compatibility tradeoff (an ad hoc `scan .` on a repo with pre-existing large, non-secret, non-excluded assets — media, fixtures — would newly start exiting 1) that this investigation surfaces but does not decide.
- **Dependencies:** The staged-mode exclude/size-check ordering gap above must be fixed in the same change (see Investigation). No dependency on `BL-003` (different module, independent code paths).
- **Design pass (2026-08-26):** Re-confirmed root cause and the exclusion-ordering gap unchanged against current source (both live-reproduced again). Full design deliberation below; nothing implemented — see Decision.
  **Complete affected code path:** `_scan_files` (single shared computation) → `run_scan` (Rich/CLI path, `console.print` + `typer.Exit`) and `scan_result` (JSON path) → `cli.py::scan` (the only caller of either — confirmed no MCP/API/other consumer of `scan_result`/`run_scan` exists anywhere in the codebase) → the installed pre-commit hook (`_generate_pre_commit_hook_content`, which always calls the *plain, non-JSON* `envshield scan --staged` and reads `$?` — this matters directly for the exit-code design below) and any external CI/hook integration.
  **Existing result/exit-code semantics, precisely:** `scan_result` returns `{"clean": not (secrets or undeclared), "secrets": [...], "undeclared_variables": [...], "skipped_files": [...]}` — `skipped_files` is populated but never read by anything downstream. `run_scan` computes `found_issues` from `all_secret_findings`/`all_undeclared_findings` only and calls `raise typer.Exit(code=1)` only if `found_issues`; `skipped_large_files` only drives a printed warning, never the exit path. `cli.py::scan`'s `--json` branch does `if not result["clean"]: raise typer.Exit(code=1)` — same gap, one level up. A structurally different case is already handled correctly and is useful prior art: `_collect_files_to_scan` raises `EnvShieldException` for a typo'd/nonexistent path, which the CLI's existing `except EnvShieldException` handler turns into `{"clean": False, "error": str(e)}` plus exit 1 (`test_scan_json_rejects_a_nonexistent_path_instead_of_reporting_clean`) — proof the "never silently claim clean" invariant is already enforced elsewhere in this same command, just not for a *partial* skip.
  **Exclusion-ordering, confirmed and the correct fix determined:** re-reproduced live — a `secret_scanning.exclude_files`-excluded 1MB+ file is correctly absent from `skipped_files` under non-staged `scan --json .` (exclusions filtered via `_filter_files` before the size check even runs), but still lands in `skipped_files` under `scan --staged --json` on the identical file/config (the staged branch's size check at `_scan_files` line 669 runs *before* the `file_path in excluded_files` branch is ever consulted). The correct ordering is subtler than "just move the check earlier": for a staged file that's excluded, the existing diff-aware logic already has three outcomes -- (a) brand-new (not in `HEAD`): scanned in full *despite* the exclusion, (b) has no new lines: nothing to scan, already `continue`s, (c) has new lines: only that bounded diff is scanned. The size check should apply to the *whole file* only in case (a), where the whole file's content is genuinely what's about to be read -- not in case (c), where only a small, already-bounded diff is scanned and a large *unrelated* excluded file (e.g. a vendored lockfile) shouldn't be flagged "incomplete" over content nobody asked to scan. Concretely: resolve `file_path in excluded_files` and run the existing new-file/no-new-lines/new-lines-only branching *first*; apply `len(content) > MAX_SCANNABLE_SIZE_BYTES` only when the file is not excluded, or is excluded-but-brand-new (i.e. whenever the full file is what's being scanned) -- never when only a diff subset is being scanned.
  **Every silent-drop mechanism found, not just size:** inspecting adjacent code for the same failure class (per the Bug-finding requirement) surfaced two more file-skip sites with *zero* result-model representation at all -- worse than the already-tracked size case, which at least appears in `skipped_files`. `_collect_files_to_scan`'s symlink protection (correct to refuse the symlink -- see its own docstring on the trust-boundary invariant) drops the path into a local `skipped_symlinks` list that's never returned to any caller; the Rich path prints an informational `ℹ️` line but `scan_result`'s `console.quiet = True` suppresses even that, so `--json` shows *nothing at all*. `_scan_single_file`'s `except (IOError, OSError): return [], []` (covering a permission-denied file, a TOCTOU-race symlink caught by `O_NOFOLLOW`, or a race-deleted file) is silent in *both* presentation paths -- not even a console message. Both live-reproduced this pass with a secret-bearing file reachable only through a symlink, and a `chmod 000` file: both report `clean: true`, exit 0, with zero trace in JSON or the terminal. **Important scoping distinction confirmed while reproducing these:** both are reachable only through non-staged `scan` (interactive or `--json`) -- `--staged` mode never calls `_collect_files_to_scan`'s symlink-filtering branch at all (`git_utils.get_staged_files()` returns early), and never calls `_open_for_scan`/hits the `IOError`/`OSError` clause (staged content comes from `git_utils.get_staged_file_content`, i.e. git's own object store, not a raw filesystem read) -- confirmed live: staging a symlink stores only the link-target *path string* as its blob content, so `--staged` mode's handling of a symlinked entry is safe by construction, independent of any EnvShield-side defense. Neither sub-case defeats the pre-commit-hook gate BL-004 itself targets, which is why they're a distinct, lower-priority finding rather than a `BL-004` scope expansion. A third, narrower case (`_get_diff_lines`'s `except Exception: return set()`, which causes an excluded staged file to be silently treated as "no new lines" -- i.e. skipped -- if diff computation itself fails) *is* inside the staged/diff-aware path and confirmed by code reading only, not live-reproduced (a git-internal failure is harder to force deterministically; same evidence-tier reasoning as `BL-093`) -- this one, if ever live-confirmed, would be the more concerning of the three for hook-gate bypass risk specifically. Recorded as new finding **`BL-095`**, not fixed here. This directly answers one of this pass's required questions: **no, the fix must not be scoped only to >1MB files** -- the *field* representing completeness must be named and defined generically (`complete`, not e.g. `all_files_under_size_limit`), even though this pass's actual implementation only populates it from the size-skip case; `BL-095`'s eventual fix should extend the same field's population, not redesign it.
  **Design options evaluated:**
  - **(A) Any skip makes `clean=false` and exit non-zero, unconditionally, in every mode.** Maximally simple and maximally secure against the invariant, but collapses "found a real problem" and "couldn't verify everything" into one bit -- a machine consumer loses the ability to tell them apart (directly fails the "can users distinguish clean from not-fully-scanned" question). Highest false-positive/compatibility cost: an ad hoc `scan .` on a repo with a pre-existing, legitimate large asset nobody ever excluded would newly start exiting 1 on every run, unrelated to anything the developer just did.
  - **(B) A distinct `complete`/`incomplete` field alongside `clean`, `clean` unchanged.** Correct and honest *as a data model* -- `clean` keeps its precise, narrow meaning ("no findings among what was inspected"), and a new field states whether coverage was actually total. Taken completely literally ("preserve clean" as in *also* preserve today's exit-code derivation from `clean` alone) this does **not** by itself close BL-004 -- the hook/CI still read only the exit code, so the fix must also change what drives the exit code, not just add an unused field. The real value of B is distinguishability, not exit-code correctness by itself.
  - **(C) Incompleteness is fatal only for CI/hook-facing modes.** Matches BL-004's own originally-recorded "Expected behavior" line verbatim. Whether this satisfies the stated security invariant depends on *what* varies by mode: the invariant is about the domain result never asserting a false "clean" claim -- a truthful data model (see B) satisfies that in every mode, regardless of what any one mode's exit code does with it. Exit code is a *policy* decision (should automation treat this as a failure), not a truth claim, so it's legitimate for it to vary by context the way `--staged` vs. bare `scan` already differ in other ways (git-ignored-file handling, diff-aware scanning). Lowest false-positive/compatibility cost for interactive use; fully closes the *evidenced* gap as long as the fatal set includes every mode the hook and typical CI usage actually invoke.
  - **(D) Other:** considered and rejected -- a separate "coverage check" command (new CLI surface for one boolean, heavier than reusing `scan`'s own existing touchpoint) and removing the size-skip mechanism entirely (defeats `MAX_SCANNABLE_SIZE_BYTES`'s own documented reason for existing -- memory/cost, not correctness).
  **Recommended semantic model: B + C combined.** `clean` keeps its exact current meaning and computation, unchanged. A new top-level `complete: bool` (`True` iff no eligible file was skipped, for any currently-tracked reason -- today only size) is added to the shared domain result, computed once in `_scan_files`/`scan_result` (not duplicated per presentation path -- this is exactly the "two independent computations that could quietly drift" pattern `_scan_files`'s own docstring already exists to prevent). The exit-code/pass-fail *policy* -- not the JSON fields -- is what varies by mode: fatal (`not clean or not complete`) whenever `--json` is used (JSON output is inherently a machine/automation signal) **or** whenever `staged_only` is true, in *both* the Rich and JSON paths -- this second condition is not optional, because the installed hook invokes plain, non-JSON `envshield scan --staged`, and a fix that only changed the `--json` branch's exit code would leave the actually-evidenced hook-bypass completely open. A bare interactive `scan` (no `--staged`, no `--json`) keeps today's behavior exactly: an informational warning, exit 0. This directly answers the pass's specific questions: `clean=true` should remain *possible* when eligible content wasn't inspected (it's a narrow, honest claim about findings only, not an overall verdict) as long as `complete` is also surfaced and the exit code/any single top-level "did this pass" signal accounts for both; yes, "incomplete" should be first-class (a named boolean, not inferred from list length by every consumer); no, exit code and the semantic result should not be forced to be the same thing -- domain truth stays constant across modes, policy legitimately varies; yes, the distinction belongs in the domain result (`scanner.py`), not presentation, and the recommended design keeps it that way.
  **Fundamental model-capacity check (per explicit instruction to state this before implementation, if true):** the current result model does **not** fundamentally lack the capacity to represent "clean but incomplete" -- `skipped_files` already carries the exact raw signal needed; the bug is purely that nothing downstream ever converts `skipped_files` non-empty into an honest top-level verdict. No redesign is needed, only an additive field plus a policy wire-up.
  **Recommended CLI/JSON/exit-code contract:** `scan_result` gains `"complete": bool` alongside the four existing keys (`skipped_files`'s own existing shape -- a flat list of path strings -- stays unchanged, for backward compatibility with any existing consumer that already reads it; a future richer per-reason shape is `BL-095`'s own deferred design question, not resolved here). `cli.py::scan`'s `--json` branch's exit condition becomes "`not result["clean"] or not result["complete"]`". `run_scan`'s exit condition gains the equivalent for `staged_only` specifically (bare `--staged` must also become fatal on incompleteness, matching the hook's literal invocation); a bare, non-staged `scan` keeps exit 0 with only the existing informational warning.

### BL-095 — `scan` silently drops a symlinked, unreadable, or diff-failed file from coverage with zero representation in any output, including the new `complete` field
Type: `SECURITY` · Evidence: `CONFIRMED` (all 3 sub-cases now directly tested — 2 via real CLI, 1 via direct function-level testing with a realistic simulated failure) · Priority: **P1**
Source(s): Discovered while investigating `BL-004`, inspecting adjacent scanner code for the same "silent skip" failure class; re-verified and deepened in a dedicated 2026-08-26 investigation, now that `BL-004`'s `complete` field exists to test against.

### BL-102 — `undeclared` has zero visibility into a wholesale environment spread (`{**os.environ}` / `{...process.env}`)
Type: `DISCOVERY` · Evidence: `CONFIRMED` (live-reproduced, both languages) · Priority: P2
Source(s): Discovered while independently verifying a DeepSeek external-report claim (`BL-060`) that "the AST visitor doesn't traverse comprehensions" — that specific claim is false (see below), but investigating it surfaced this separate, real, previously-untracked gap.

- **Problem:** `discovery.py`'s Python visitor (used by `undeclared`) only records a usage when it recognizes a specific call shape (`os.environ.get(...)`, `os.getenv(...)`) or a subscript with a *literal* string key (`os.environ["X"]`). A wholesale unpack — `{**os.environ, ...}` in Python, `{...process.env, ...}` in JS/TS — touches every environment variable at once but names none of them individually, so nothing in the current model has anything to record. This is structural, not an oversight in one code path: `DiscoveredVariableUsage.variable` is a single string, and a spread has no single string to put there.
- **Not the same claim DeepSeek made, and DeepSeek's claim is refuted, not confirmed:** DeepSeek's report attributed the symptom to "the AST visitor doesn't traverse comprehensions or spread operators." Live-tested directly: a literal-string call *inside* a comprehension body (`{os.environ.get("LITERAL_IN_COMP"): 1 for x in range(1)}`) **is** correctly detected, at the correct line — comprehensions are traversed fine via the visitor's default `generic_visit` recursion. The real, narrower cause for a variable-keyed subscript inside a comprehension (`os.environ[key] for key in [...]`) is that `key` is a variable, not a literal, and `_literal_str` only resolves `ast.Constant` string arguments — a separate, expected, already-implicit scope boundary (`DiscoveredVariableUsage.confidence = "high"` implies no heuristic/computed-key guessing is attempted), not a bug, and not release-relevant on its own.
- **Evidence/reproduction (2026-08-26), both languages, live-tested against real `discover_python_usages`/`discover_js_usages`:**
  - Python: `merged = {**os.environ, "CUSTOM": "value"}` → **zero** usages recorded. A normal literal access (`os.environ.get("NORMAL_VAR")`) in the same snippet **is** correctly recorded, confirming the visitor runs at all and the spread specifically produces no signal.
  - JS/TS: `const merged = {...process.env, custom: "value"};` → **zero** usages recorded, while `const { DB_HOST, DB_PORT } = process.env;` (ordinary destructuring, in the same snippet) **is** correctly recorded (both names found) — confirming destructuring works and the spread specifically is invisible.
- **Why this is more than a contrived edge case:** `{**os.environ, ...}` / `{...process.env, ...}` is not an unusual pattern — it's the standard, idiomatic way to spawn a subprocess/child process that inherits the full parent environment plus a few overrides (`subprocess.run(cmd, env={**os.environ, "EXTRA": "1"})` in Python; `child_process.spawn(cmd, {env: {...process.env, EXTRA: "x"}})` in Node.js). A codebase using this ordinary idiom gets no `undeclared` signal at all for that entire code path, no matter what it does with the merged result.
- **Classification:** A representational limitation of the discovery model, not a bug and not a false-clean. `undeclared`'s job is reporting a *specific new dependency the schema doesn't know about*; a spread doesn't assert any specific variable is newly depended-on, so there's no wrong verdict here — there's an absence of any verdict, silently. This is the correctness-relevant distinction: not "EnvShield reports something false," but "EnvShield reports nothing about a code path that, in the wholesale-secret-exposure case, is exactly the kind of thing a configuration-integrity tool exists to have an opinion about."
- **Security framing, deliberately bounded:** this is **not** a vulnerability in EnvShield — EnvShield doesn't leak anything itself. It is a completeness gap in one command's coverage, conceptually adjacent to (but a different mechanism from) `BL-095`'s already-tracked silent-scan-skip gaps: both are cases where a real, evidenced code path produces zero signal from an EnvShield command whose entire purpose is producing signal about exactly that kind of thing.
- **Checked and confirmed absent from existing documentation** before recording: no mention anywhere in `BACKLOG.md`, `README.md`, `CLAUDE.md`, or `AGENTS.md` (`grep` for "spread"/"wholesale"/`**os.environ`/`...process.env` — the one hit was an unrelated phrase about `add_service`'s dict-replacement semantics). README's own "Known limitations" section documents the *language* boundary (Python AST-based, JS/TS pattern-based, no other languages yet) but not this specific gap within the two languages it does support.
- **Dependencies:** None. Independent of `BL-013` (JS/TS discovery is pattern-based generally, `NEEDS_EVIDENCE`) — that item is about missing file extensions/dynamic access broadly; this is a specific, confirmed representational gap in both the Python and JS/TS paths.
- **Decision:** Open, backlog. Not implemented — recorded as a finding only, per this reconciliation pass's explicit scope (evidence hygiene, not engineering work).
- **Target:** Unscheduled. Any eventual fix would need a real design decision (e.g., a new usage category for "wholesale access, no specific variable identified" rather than trying to force a spread into the existing single-variable-name model) — not attempted here.

### BL-105 — A `defaultValue` contradicting its own declared type loads without complaint
Type: `RELIABILITY` · Evidence: `CONFIRMED` · Priority: P2 · Status: **fix implemented and tested, deferred out of `4.6.1`**
Source(s): 2026-08-30 Zeus clean-adoption audit; reproduced directly against schema loading, independent of Zeus.
Component: `core/schema_types.py` (new `default_value_type_conflict` predicate), `config/manager.py` (load-time rejection), `core/exceptions.py`

- **Problem:** A schema could declare a `defaultValue` its own `type`/`enum`/`pattern` rejects — e.g. `type = "bool"` with `defaultValue = "no"` — and load with no error. Every downstream surface then treated that same value as invalid: `check` reported the schema's own default as an `Invalid Value` (`must be 'true' or 'false'`), while `.env.example`, `setup`, and generated code carried it verbatim. A contract that contradicts itself.
- **Deliberately NOT the fix:** widening `bool`. Its narrow `true`/`false`-only definition is intentional and already locked in by `test_validate_value_bool_only_accepts_true_false`; a project using `yes`/`no` flags models them as `enum = ["yes", "no"]`, which works correctly today and is regression-tested as part of this fix. This item refuses a self-contradictory schema; it does not touch the type system.
- **Fix (2026-08-30):** New pure predicate `schema_types.default_value_type_conflict(field_schema)`, which delegates to the existing `validate_value` so the rule can never drift from what the rest of the product validates against, and returns the constraint reason (never the value). Rejected at load via `config_manager._reject_invalid_defaults`, called from `load_schema`/`load_bare_schema` immediately after `_reject_secret_defaults` — the same post-`extends`-merge choke point, for the same reason `BL-001` used it: one guard, every consuming command. A missing or empty-string `defaultValue` is never a conflict, exactly mirroring `secret_default_conflict`'s own empty-string carve-out.
- **Backward-compatibility:** this is a **behavior-narrowing** change. A schema that previously loaded with a self-contradictory default would newly fail at load with `InvalidDefaultValueError`. EnvShield's own built-in `init` templates declare no `type` at all (so they resolve to unconstrained `string`) and are unaffected, and the full suite passed unchanged with the fix applied — but an existing user's committed schema *can* newly error, which is exactly what a patch release must not do.
- **Tests (written, passing, then held back with the fix):** `test_schema_types.py::TestDefaultValueTypeConflict` (10 cases — bool/int/port/url/email/float/enum/pattern, untyped-accepts-anything, missing-and-empty carve-outs, and a check that the reason never echoes the value) and `test_config_manager.py::TestLoadSchemaRejectsDefaultsThatContradictTheirType` (6 cases — `load_schema`, `load_bare_schema`, caught after the `extends` merge, all offenders named at once, valid defaults still load, and the `yes`/`no` enum workaround still loads).
- **Decision: DEFERRED to the next minor (not `4.6.1`).** The fix is fully implemented, tested (16 cases, all passing, all confirmed failing beforehand), and reviewed — then deliberately reverted out of the `4.6.1` working tree, because `4.6.1` is a patch release for `BL-104` and this is the one change in the set that can make a previously-working project fail. Shipping it in a patch would violate the repo's own patch/minor/major convention. ### BL-106 — Service-scoped source discovery cannot see a shared internal library
Type: `ARCHITECTURE` / `DISCOVERY` · Evidence: `CONFIRMED` · Priority: P2 · Status: **fixed and tested, not yet released**
Source(s): 2026-08-30 Zeus clean-adoption audit; live-reproduced with a controlled two-file experiment.
Component: `config/manager.py` (new `get_service_additional_source_roots`), `core/dependency_snapshot.py`, `core/explain.py`

- **Problem:** `undeclared` and `explain` only ever walk a registered service's own directory. A shared internal library that lives outside every service directory — imported by several services, and containing real environment reads on their behalf — is invisible to both, for every service.
- **Evidence/reproduction:** In a pristine clone of a real two-service monorepo, one new `os.getenv` read was appended to a shared library outside both service directories (`modules/phineas/`, 33 real env reads, volume-mounted into both containers) and one to a service's own file. `envshield undeclared --service athena` reported only the service-local read; the library read was absent. The no-`--service` form, which iterates every registered service, also missed it for both. `scan` is **not** affected — it is repo-wide and reported all 53 of that library's rows, so this is specific to the service-scoped commands.
- **Impact:** A developer adding `os.getenv("NEW_FLAG")` to the shared library gets a clean `undeclared` and a passing pre-commit hook while introducing a real, undeclared configuration dependency for every service that imports it. A false negative, though a narrow one: it requires the read to be in a directory no registered service owns.
- **Workaround that already works, with no code change:** register the library as its own service with its own schema — verified closing the gap completely in the same experiment. It is slightly wrong-shaped (the library is not an application) but it is coherent: the library genuinely has its own configuration surface, and `extends` can then compose that surface into each consuming service's contract.
- **Smallest general model (assessed, not implemented):** the missing relationship is "service A depends on shared configuration surface L," where L is neither a service nor a deployable. Anything built here must express that without making L an application — e.g. a `depends_on:`-style list of additional source roots contributing to a service's discovery scope, which `dependency_snapshot`/`explain` would union into their walk. Deliberately not designed further here: this is exactly the kind of relationship the future Configuration Graph (`BL-103`) exists to model, and building a one-off ahead of it would prejudge that design. Recorded so the requirement survives.
- **Dependencies:** Related to `BL-103` (the prototype inherits this same blind spot: a cross-service relationship mediated *only* through a shared library's source, with no `extends` link and no shared manifest entry, cannot be proven by either of its two accepted evidence types).
- **Second, independent evidence instance (2026-09-01, Zeus dogfooding — `BL-113`'s Flask marginal-value quantification):** tracing all 48 distinct Flask-config keys read in Zeus found exactly 5 genuinely undeclared anywhere in the repo (`PADDLE_API_KEY`, `PADDLE_SANDBOX`, `PADDLE_WEBHOOK_SECRET_KEY`, `POSTMARK_API_KEY`, `PHINEAS_TEST_MODE`) — every one of them read exclusively from inside `modules/phineas/`, the same shared library this item already names. This raises this item's real-world impact: it isn't only an `os.getenv`-shaped gap, it's the actual reason a second, independently-discovered category of real secrets (a payment provider's API key and webhook secret, an email provider's API key) is invisible to `undeclared`/`explain` in Zeus today, regardless of what access syntax reads them.
- **Fix (2026-09-03) — a joint design gate (see this same day's session record) evaluated this item alongside `BL-113` and authorized this one only, narrowly, per the smallest-general-model sketch above, revised on review:**
  - **Rejected `depends_on:` as the key name** — it reads as a dependency-graph/build-order edge and collides semantically with Docker Compose's own `depends_on:` key sitting in the same file. Shipped as **`additional_source_roots`** instead, a plain list of extra directories under a service's entry in `envshield.yml`.
  - **New `config_manager.get_service_additional_source_roots(name) -> List[str]`**, mirroring `get_service_completeness_mode`'s exact shape (empty list if unset, opt-in only, never inferred). Each entry is validated through the pre-existing `_ensure_within_project` — the same supply-chain protection `schema`/`local_file`/`example_file` already have; a root resolving outside the project (including via a symlink) raises `UnsafePathError`, not a silent skip.
  - **`discovery.py` was not touched at all** — proven from its own call graph before implementation: its two public entry points take already-read file content and a label, with no concept of a service, directory, or root. The whole fix is in the two callers that decide *which files* get read.
  - **`dependency_snapshot.py::discover_usages_for_service`** now filters the (already git-deduplicated) changed-file list against `[service_dir] + additional_roots` via `any(...)`, instead of `service_dir` alone — a single membership test per file, so an overlapping/nested root cannot produce a duplicate row here by construction.
  - **`explain.py`** now walks `[service_dir] + additional_roots` (via `_discover_current_usages`, its `_discoverable_files` helper generalized to take any root, not just a service's own directory) and deduplicates by normalized file path (`seen_files`) before reading a file a second time — needed here specifically because, unlike `dependency_snapshot.py`, this path performs a fresh directory walk per root and would otherwise double-report a file reachable through two overlapping roots.
  - **Symlink handling required no new mechanism**, exactly as designed: an additional root that is itself a symlink is refused by `_discoverable_files`'s pre-existing, unconditional `os.path.islink(root_dir)` check — the same guard a service's own directory already had — independently of `_ensure_within_project`'s separate (and separately triggered) boundary check for a root resolving entirely outside the project.
  - **A nonexistent root is a silent no-op** — `os.walk`/`service_dir_contains` already tolerate this gracefully; no new error path was added, matching the design gate's explicit scope limit.
  - **The same root may legitimately be listed by more than one service** — verified: no ownership/exclusivity claim is made or needed, matching the "shared configuration surface" framing this item has always used, and this doesn't introduce any new provenance/ownership model.
  - **`scan` is unmodified** — it was already repo-wide, confirmed unaffected by design and by an unchanged diff.
  - No dependency graph, provenance system, plugin registry, or new abstraction was introduced — the entire fix is a widened file-enumeration boundary in two existing, already-per-service walks.
- **Tests (20 new, all passing, full suite 1097/1097):** `test_config_manager.py` (5 cases — default-empty, reads the key, unknown service, path-outside-project rejection, non-list value ignored), `test_dependency_snapshot.py::TestAdditionalSourceRoots` (6 cases — one root, multiple roots, nonexistent root, nested/overlapping root produces no duplicate, the same root shared by two services, absent-key regression), `test_explain.py::TestAdditionalSourceRoots` (7 cases — the same matrix plus a symlinked-root refusal, specifically constructed to exercise `_discoverable_files`'s own guard rather than `_ensure_within_project`'s separate boundary check), and one real-CLI end-to-end test each in `test_undeclared_cli.py`/`test_explain_cli.py` (`--service api` against a real registered `additional_source_roots` entry, not just the internal `build_report`/`discover_usages_for_service` helpers).
- **Verification:** full suite 1097/1097, `ruff check .` clean, `discovery.py` diff confirmed empty, a fresh disposable read-only Zeus dogfooding pass reconfirmed the original two-file reproduction now closes cleanly with `additional_source_roots` configured (no Zeus files left modified — `git status`/`md5sum` re-verified clean before and after).

- **Tests:** `test_explain.py::TestBuildUndeclaredReport` (3 cases) plus `test_explain_cli.py::TestExplainNotFound`'s three pre-existing tests rewritten (not silently deleted — see their own updated docstring) to assert the new graceful-degradation behavior instead of the old bare-error one, plus one new case (source read named in plain-text output).

### BL-113 — Framework-aware Python configuration discovery (Flask `current_app.config` recognition)
Type: `DISCOVERY` (feature) · Evidence: `CONFIRMED` (two independent real codebases) · Priority: P2 · Status: **fixed and tested, not yet released**
Source(s): Surfaced by `BL-109`'s real-world fix (a Zeus codebase's central config module used `from os import getenv` exclusively, invisible to discovery) and the Zeus dogfooding evaluation's finding that `app.config[...]`/Django `settings.X` are entirely outside discovery's scope. Design work performed this session; see ROADMAP.md's Exploring section for the product-facing summary this entry backs.

**What this record exists to preserve:** the design reasoning behind ROADMAP.md's "Framework-aware configuration discovery within Python" Exploring item, so it survives independently of chat history. **Nothing described here is implemented.** Per `CLAUDE.md`/`AGENTS.md` §3 principle 7 (added alongside this entry), `BL-109`'s narrow fix shipping does not authorize any of this.

- **Current architecture, precisely:** four call sites (`scanner.py`/`scan`, `dependency_snapshot.py`/`undeclared`, `explain.py`/`explain`, `importer.py`/`import`+`service discover`) all dispatch through `discovery.py`'s `discover_python_usages`/`discover_js_usages`/`discover_python_env_vars` — one shared module reaches all of them. `DiscoveredVariableUsage` (variable, file_path, line, language, access_type, confidence) is already framework-agnostic; a Flask/Django read fits this exact shape with a new `access_type` string, no new output type needed.
- **Proposed architecture (revised 2026-08-31 — see "Why the registry was rejected" below; this replaces the entry's original `ConfigAccessProvider`/registry sketch, not an addition alongside it):** extend the existing `_OsBindings`/predicate pattern `BL-109` already established — no new interface. Each framework gets its own bindings dataclass (`_FlaskBindings`, `_DjangoBindings`) and its own named predicate function(s) (`_is_flask_config_read`, `_is_django_settings_read`), called directly from `_UsageVisitor`'s methods (`visit_Call`/`visit_Subscript` for Flask's shape; a new `visit_Attribute` for Django's) — a short, fixed sequence of calls to named functions, not a dynamic loop over a registered list. **No `Protocol`, no provider base class, no plugin registry.** All top-level import evidence (`os`, `flask`, `django.conf`, ...) is collected in **one shared pass per file**, not one pass per framework — the original design's one-`prepare()`-call-per-provider shape was rejected specifically because it would re-scan the same file's imports once per registered framework, redundant cost that scales with framework count on top of an already-measured 17–23s repo-wide `scan` cost on a real ~7,800-file monorepo (Zeus evaluation).
  **Why the registry was rejected, not just simplified:** the real extension set is two, maybe three frameworks, ever — nothing in the product needs third-party-registered providers at runtime, and Flask's Call/Subscript shape and Django's Attribute shape share so little (Django has no literal-string key to extract at all) that a shared Protocol barely reduces duplication between them. The existing predicate-function pattern already proved genuinely additive — `BL-109` extended it with zero new interface — so a formal registry would be solving a problem (many pluggable frameworks) this codebase doesn't have.
- **Flask: reads vs. population are two different problems.** Reads (`app.config["FOO"]`, `.get(...)`, `current_app.config[...]`/`.get(...)`) are structurally identical to today's `os.environ[...]`/`os.getenv(...)` shape (literal string key) — this is the part worth building. Population (`app.config.from_pyfile(...)`/`from_object(...)`/`from_mapping(...)`/`from_envvar(...)`) doesn't name a variable at the call site at all — it names a file/object whose own contents need separate, cross-file resolution, architecturally closer to `service discover`'s existing schema-seeding than to a single-file AST read-recognition problem. **Population is explicitly excluded from this direction** — a separate, harder, not-yet-designed capability.
- **False-positive strategy (the specific risk flagged before this design started):** never match a bare `anything.config["FOO"]`. Two-tier confidence: `current_app.config[...]`/`.get(...)` is high-confidence once `from flask import current_app` is confirmed present (a top-level-only import check, mirroring `BL-109`'s own `_collect_os_bindings` cost discipline) — `current_app` is Flask's own specifically-named proxy, low ambiguity. A local `app.config[...]` is only matched when the same file also visibly constructs it (e.g. `app = Flask(__name__)`) — corroborating evidence required, not name-matching alone. `DiscoveredVariableUsage.confidence` (already a field, always `"high"` today) gets its first real use for `"medium"` here.
- **Django's `settings.FOO` is attribute access, not a call/subscript** — there's no literal string key; the attribute name *is* the variable name, structurally closer to the existing `BaseSettings`-class-attribute recognition (`_visit_base_settings_field`) than to the os/Flask Call/Subscript shape. Requires its own `visit_Attribute` hook on the shared visitor, gated the same way (`from django.conf import settings` must be visibly present — `settings` alone is too common a name to match unconditionally).
- **What stays framework-agnostic:** the schema itself (no new field for "access mechanism" — `access_type` is already a per-usage discovery detail); `service discover`'s seeding path (seeds from a service's `local_file`'s own literal *declarations*, a structurally different concern from *reads*, untouched by this direction); the CLI surface (no new flags or `envshield.yml` keys proposed — recognition activates from evidence already inside each file, the same way today's Python-vs-JS dispatch already works from the file extension alone).
- **Genuine architectural tension, named rather than hidden:** `discovery.py`'s own docstring states "no alias or import-indirection tracking" as a founding scope philosophy. `BL-109` already nudged this (one specific bare-import form); framework recognition pushes it further still (confirming `current_app`/`settings` were actually imported before trusting them). This is a conscious expansion of that philosophy, not a free extension of it.
- **Smallest next step, if this direction is ever authorized:** add `_FlaskBindings`/`_is_flask_config_read` following `_OsBindings`'s exact existing shape, fold its import check into the same shared top-level-import pass `_collect_os_bindings` already does, and wire it into `visit_Call`/`visit_Subscript` alongside the existing os predicates — a small, additive change, not a refactor of anything existing. Django's `visit_Attribute` addition should follow only once Flask's addition is proven behavior-neutral against the full existing suite, not built in the same pass.
- **Decision:** Design proposal only. Not implemented, not committed to a release, not scheduled. Recorded in ROADMAP.md's Exploring section (real product direction, demand/design not yet validated enough to commit) — not "Next," and explicitly not the same direction as the pre-existing "source-language discovery beyond Python/JS-TS" Exploring item (that's about additional *languages*; this is about additional *ways Python code reads configuration*).
- **Target:** Pending explicit authorization to (a) approve this revised architecture on its own merits, and (b) begin with the `_FlaskBindings`/`_is_flask_config_read` addition above — not full Flask/Django implementation in one pass, and not the originally-proposed registry shape.
- **Marginal-value quantification (2026-09-01, Zeus dogfooding pass) — the raw call-site count materially overstates this direction's value.** The prior pass's evidence (340 `app.config`/`current_app.config` call sites, 105 files, 48 distinct keys) was volume evidence, not gap evidence — it says how often Flask-style access is used, not how much of it is actually invisible to EnvShield today. Traced all 48 distinct keys against Zeus's real, checked-in config files and its actual `envshield.yml` service registration:
  - **22/48 (46%) are already declared today**, through the `env_config.local.py` files already registered as each service's `local_file` — zero benefit from Flask-read recognition; these variables are already schema-visible via the existing, unrelated declaration mechanism.
  - **16/48 (33%) are declared in the repo, just in `app_config.py`, a second config file that isn't currently registered.** Not a discovery gap at all — a **registration/workaround** question (`BL-030`/`BL-025` territory: EnvShield's single-`local_file`-per-service model can't express "config comes from two Python files"). Flask-read recognition wouldn't close this; multi-source completeness would.
  - **10/48 (21%) are absent from every checked-in config file.** Traced individually, not assumed: **5 are Flask/Flask-SQLAlchemy-internal or runtime-computed** (`SQLALCHEMY_DATABASE_URI`/`SQLALCHEMY_BINDS` are built at runtime from already-declared `DB_*` variables — `f"mariadb+pymysql://{db_user}:{db_pass}@{db_host}/{db_name}"` in `hermes/app/setup.py`/`athena/app/setup.py`; `TESTING`/`SERVER_NAME`/`SESSION_COOKIE_DOMAIN` are Flask built-ins never assigned as a literal anywhere in the repo) — **noise**, not variables a schema should track regardless of any Flask-discovery feature. **The remaining 5** (`PADDLE_API_KEY`, `PADDLE_SANDBOX`, `PADDLE_WEBHOOK_SECRET_KEY`, `POSTMARK_API_KEY`, `PHINEAS_TEST_MODE`) are genuinely undeclared anywhere in the repo — populated in production from a build-time, AWS-SSM-generated `env_config.py` not present in the repo (per its own comment: "generated at build time using `./app/scripts/build_env_config.py` ... pulls everything from ParameterStore") — and are read exclusively from inside `modules/phineas/`, the **same shared library `BL-106` already documents as outside every service's own directory.**
  - **The actual conclusion: zero of the 48 keys are a case where Flask-read recognition alone would be both necessary and sufficient to close a real gap.** Every one of the 5 genuinely-invisible keys is invisible because of `BL-106`'s already-tracked shared-library blind spot, not because of the *access syntax* (`app.config[...]` vs. `os.getenv(...)`) used to read them — if `BL-106` were fixed and `modules/phineas/` were reachable by service-scoped discovery, plain literal-string recognition of `os.environ`-shaped reads inside that same library would already exist for whichever of those 5 keys are *also* read via `os.getenv` anywhere (worth checking before any further investment) — Flask recognition specifically would only add value for keys read *exclusively* via `app.config[...]` inside a location discovery can already reach, and this trace found none in Zeus's actual code.
  - **What this changes and doesn't change:** doesn't refute that Flask-read recognition could have value on a different, real codebase — it's still a plausible general capability. It does mean **this specific piece of evidence (Zeus) argues less strongly for `BL-113` than the raw 340-call-site number suggested**, and argues more strongly for `BL-030` (multi-source completeness, would close the 16-key gap) and `BL-106` (shared-library discovery, would close the 5-key genuine gap) — both already independently justified, neither Flask-specific. This is exactly the "smallest general fix" question this pass's process asks for: the smallest fix that closes Zeus's *actual* invisible-configuration problem is `BL-106`, not `BL-113`.
- **Reopened, second-codebase evidence study (2026-09-03) — a real justification, distinct from the (still-refuted) undeclared/completeness one above.** `explain`'s own core promise ("what source code reads this variable") was measured, exhaustively, to return a false "None discovered" for 91–95% of Zeus's declared schema variables, because the majority of Zeus's real reads are `app.config[...]`/`current_app.config[...]`, invisible to `os.environ`/`os.getenv`-only recognition. A second, independently-chosen, application-factory-pattern codebase ([CTFd](https://github.com/CTFd/CTFd)) was studied specifically to stress-test the design's weakest link before committing to it — and **invalidated two of the original design's three components while confirming the third:**
  - **The originally-proposed `<name> = Flask(...)` local-construction heuristic is nearly useless in practice.** CTFd never calls `Flask(...)` directly in production code — it subclasses it (`class CTFdFlask(Flask)`), invisible to a literal-call match. Zeus does call `Flask(...)` directly, but only in its two app-factory files; the vast majority of both codebases' real reads are in files that never construct anything. **Dropped entirely**, not merely deprioritized.
  - **The dominant real-world pattern in both codebases is `from flask import current_app as <alias>`, not the literal `current_app` name** — 84% of CTFd's measured Flask-config reads (109/129), 89% of Zeus's (374/422). The original design's own text mentioned aliasing only to explicitly exclude it, conflating this import-time renaming with the genuinely rare *assignment*-style aliasing (`config = current_app.config`, confirmed 0 occurrences in both codebases). These are different patterns with very different frequencies; **the alias form is now tracked**, the assignment form remains excluded.
  - **A majority of `from flask import current_app` imports are function-local/deferred, not top-level** — 75 of 140 (54%) in Zeus, an idiomatic pattern (avoiding Flask's app-context/circular-import issues at module load time) that is common, not the rare exception `_OsBindings`'s top-level-only scan assumed for `os`. **The binding scan is a full `ast.walk`, not top-level-only**, gated behind a cheap `"current_app" in content` prefilter so a file with no Flask involvement pays no extra cost.
  - **A real false positive was found and confirmed automatically excluded with no extra logic**: Zeus's `self.gateway.config.get("is_direct")` (an unrelated payment-gateway object's own settings dict). Its base is an `ast.Attribute` chain (`self.gateway`), never a bare `ast.Name`, so the same bare-Name-only shape `_is_os_environ` already requires excludes it by construction.
  - **Module-qualified `flask.current_app...` and assignment-based aliasing are confirmed absent (0/0) in both codebases** — the original design's exclusion of both is now doubly evidenced, not merely assumed.
- **Fix (2026-09-03), implementing exactly the narrowed, evidence-supported scope above — `explain`-only, per this same day's product-semantics decision:**
  - `discovery.py`: new `_FlaskBindings` (the set of local names bound to `current_app` via `from flask import current_app [as <alias>]`, collected by `_collect_flask_bindings`, a whole-file `ast.walk`) and two new predicates (`_is_flask_config_attr`/`_is_flask_config_get`), wired into the existing `visit_Call`/`visit_Subscript` — no new visitor method, no registry, no Django support (zero evidence for it, ever). A recognized Flask read is reported at `confidence="medium"`, never `"high"` — `DiscoveredVariableUsage.confidence`'s first real use. `discover_python_env_vars`/`_EnvVarWithDefaultsVisitor` (the schema-seeding engine) is untouched — auto-seeding a schema field from a medium-confidence, indirection-based read is a separate, unrequested, riskier capability.
  - **A real design gap found and fixed during implementation, not anticipated in either prior gate:** `discover_python_usages` is the single shared entry point for `explain`, `undeclared` (via `dependency_snapshot.py`), and `scan` (via `scanner.py`) alike. Implementing Flask recognition there unconditionally would have silently flowed medium-confidence findings into `undeclared`'s missing-declaration detection and `scan`'s own undeclared-variable listing — live-verified directly: before this second fix, a disposable Zeus scan's `undeclared_variables` count changed from 206 to 348 findings, and a minimal reproduction confirmed `undeclared` would report a brand-new Flask-only read as a missing declaration. Both call sites now filter to `confidence == "high"` before their own downstream logic (`dependency_snapshot.py::_discover`, `scanner.py::_record_discovered_usages`) — `explain.py` is the only caller that keeps medium-confidence usages. Re-verified against the same Zeus scan: `undeclared_variables` byte-identical (206/206) before and after; a minimal reproduction confirmed `undeclared --json` reports `has_missing_declarations: false` for a newly-added Flask-only read that `explain` simultaneously shows at medium confidence.
  - **CLI**: `explain`'s human-readable "Used in source" section appends `(medium confidence)` inline for any non-`"high"` usage — the smallest change that keeps the distinction visible at the point of reading rather than only in `--json`. `--json` needed no shape change — `confidence` was already emitted on every row.
  - **Deliberately not implemented, per the evidence above:** local `Flask()`/subclass construction tracking, `self.config` inside a Flask-subclass method (real but low-volume: 2 occurrences in CTFd, 6 in Zeus — would require class-hierarchy tracking), module-qualified `flask.current_app` access, assignment-style aliasing, Flask config *population* tracing (`from_pyfile`/`from_object`/etc.), and any Django support.
  - **Performance, measured against real Zeus** (same methodology as `BL-050`/`BL-114`): repo-wide `scan` was 17.20s before this fix; 16.83–17.06s after (two runs) — within run-to-run noise, no measurable regression. The `"current_app" in content` prefilter confirmed effective.
  - **Dogfooded against real Zeus, read-only** (`explain` never writes): the two Zeus variables named in the original evidence (`DB_HOST`, `STRIPE_PLATFORM_FEE_BPS`) now correctly show their Flask reads at medium confidence instead of "None discovered." Re-running the prior pass's exhaustive per-schema-key measurement: athena's "None discovered" rate fell from 58/61 (95%) to 20/61 (33%); hermes's fell from 30/33 (91%) to 12/33 (36%) — a large, real improvement in `explain`'s core promise, with the remaining gap attributable to genuinely-unused fields, Flask built-ins, and the function-parameter-passed-app-object case this design correctly declines to resolve (cross-file, out of scope by design).
  - **Tests:** `test_discovery.py` gained `TestFlaskCurrentAppConfigRead`, `TestFlaskConfigAliasedImport`, `TestFlaskConfigDeferredImport`, `TestFlaskConfigFalsePositives`, `TestFlaskConfigAliasingOutOfScope`, `TestFlaskConfigCoexistsWithOsRecognition` (19 new cases covering every recognized pattern, every excluded pattern, and the false-positive/deferred-import findings above as explicit regression tests). `test_explain_cli.py` gained `TestExplainFlaskConfidence` (3 cases: medium-confidence inline text, high-confidence shows no caveat, `--json` carries the field). Full suite 1116/1116, `ruff check .` clean.
  - **Decision:** **Fixed 2026-09-03, in the working tree — not yet released, not yet committed.** `explain`-only scoping confirmed correct and load-bearing by this same implementation (see the `undeclared`/`scan` leak found and fixed above) — not just a cautious default, a concretely necessary one.

### BL-030 (aka G-3) — Implement `completeness: union` per the Rev 3 specification
Type: `ARCHITECTURE` / `FEATURE` · Evidence: `CONFIRMED` problem, spec `STRATEGIC` (decided) · Priority: P1 (highest product value identified across this whole engagement)
Source(s): Original Zeus audit (live-reproduced there — `schema sync` tried to append 18 Compose-owned variables into a Python file); two full adversarial spec passes since.
Component: `config/manager.py`, `core/schema_manager.py`, `cli.py`, `core/doctor.py` (see the spec's own file map for exact functions)

- **Problem:** EnvShield's single-source model can't express a legitimate contract split across multiple registered sources (Zeus: mode-switches in Compose, secrets in a Python module) — a variable satisfied by one registered source is falsely reported missing because another source doesn't have it.
- **Chosen architecture:** `completeness: union` — a per-service, opt-in flag in `envshield.yml`; a set-union over *presence* only, never over values. Deliberately **not** the earlier "Satisfaction Modes" proposal (see BL-032) — no automatic source discovery, no precedence, no merge strategies, no per-field `source` schema annotation.
- **Status:** **Implemented 2026-09-01 — see "Implementation" below.** Previously: fully specified across two adversarial review passes (Rev 2, Rev 3), published as a standalone spec artifact. **That artifact was never a file in this repository and could not be located when implementation began** (searched `docs/reports/`, the whole tree, for rev2/rev3/g3/completeness/union — nothing) — implementation proceeded from this checklist plus explicit, freshly-settled product decisions (doctor semantics, the requiredIf ambiguity rule) rather than fabricating the missing document's prose, per this file's own rule 8.
- **Implementation checklist** (each already resolved *within* the spec — tracked here as one item's sub-work, not as separate backlog rows, per the recommendation to avoid clutter):
  - `requiredIf` evaluated per-source independently, OR-reduced across sources (fixes a hidden-precedence bug found in Rev 2, backed by a worked counter-example).
  - `SourceResult`/`FieldStatus`/`FieldEvaluation` — a transient, discard-after-classification design; never retains raw values.
  - `check --json`'s new `combined` key — a top-level sibling to `results`, not a heterogeneous entry inside it, verified against two named existing tests (`test_check_json_reports_clean_state`'s exact-equality assertion, `test_json_shape_matches_check_doctor_convention`'s homogeneity rule).
  - `check`'s exit-code control flow restructured for union targets (evaluate all sources first, then decide, not an inline per-source flip).
  - "Registered-source completeness" and "Source health" kept as two structurally separate signals everywhere (CLI, JSON, `doctor`), so a source error can never hide behind a passing completeness line.
  - `doctor` wording corrected so a union-satisfied-but-locally-incomplete file is never described as self-sufficient.
  - `_evaluate_source`'s exception handling broadened to `(EnvShieldException, FileNotFoundError, OSError, SyntaxError)` plus an independent `ast.parse` pre-check for `.py` local files — see BL-031, the one item from this list that remains genuinely open.
  - The resolved-environment boundary made explicit everywhere in UI text: `completeness: union` validates registered, static sources — it is never a claim about the environment a running process actually receives.
  - `FieldStatus.PRESENT` (aka `G3-11`) — a guardrail note, not an implementation step: this status deliberately collapses "asserted" and "forwarded" values for completeness purposes; whoever builds provenance (`BL-033`) later must derive that distinction independently and must not reuse `FieldStatus.PRESENT` as if it already carried it.
  - The word "union" (aka `G3-12`) — a documentation note: `envshield.yml`'s `completeness: union` is a set-union over *presence*, not a Compose/Kustomize-style value merge; the spec's user-facing docs must say so explicitly so the two aren't conflated.
- **Dependencies:** `BL-031` closed 2026-09-01 — no longer blocking. `_evaluate_source`'s exception-content-safety question is answered for all four parsers.
- **Related:** BL-023 (explicitly must **not** be bundled into this implementation, despite being found in the same investigation; `BL-023` itself fixed 2026-09-01, see its own entry).

- **Implementation (2026-09-01).** Deliberately the smallest coherent version of the checklist above, per explicit instruction: an opt-in composition layer over the existing single-source primitives, not a rewrite, not a second schema system, no `Protocol`/registry/plugin architecture.
  - `config/manager.py`: `get_service_completeness_mode(name) -> Optional[str]` — reads `envshield.yml`'s new per-service `completeness` key (only `"union"` is meaningful today). Mirrors `get_service_config_source`'s existing shape exactly.

### BL-031 (aka G3-10) — Parser exception content-safety verification
Type: `SECURITY` · Evidence: `CONFIRMED` (all four parsers checked, 2026-09-01) · Priority: P1 (blocks BL-030's `_evaluate_source` specifically, not the architecture)
- **Problem:** Could a parser's exception message (`SyntaxError`, `YAMLError`-wrapped `EnvShieldException`, etc.) ever echo raw file content — a source line, an offending token — into `SourceResult.error` / the new `combined[].errors[]` JSON field?
- **Partial evidence (2026-08-26, found during BL-001–BL-004 post-fix verification, not a dedicated BL-031 pass):** the Python parser's contribution to this question is now directly answered — `BL-002`'s fix confirmed and regression-tested (`test_python_parser_syntax_error_message_never_echoes_the_offending_line`) that `_python.py`'s `raise EnvShieldException(f"Could not parse '{file_path}': {e}")` never echoes file content, since `str(SyntaxError)`/`str(UnicodeDecodeError)` describe only the failure (position/description), never the source line itself — live-confirmed with a sentinel secret-shaped string placed on the offending line.
- **Remaining three parsers checked directly, 2026-09-01 (Zeus dogfooding pass, investigating `BL-030`'s readiness):**
  - **`_docker_compose.py` — genuinely unsafe, confirmed by live reproduction, now fixed as `BL-115`.** `except yaml.YAMLError as e: raise EnvShieldException(f"...: {e}...")` interpolated `str(e)` directly; PyYAML's `YAMLError.__str__()` renders a code-context snippet that includes the actual offending line's text. Reproduced with a secret-shaped string (`AKIA-NOT-A-REAL-AWS-KEY_SECRET-PLACEHOLDER-VALUE`) on a deliberately malformed line: it appeared, truncated but real, inside the raised `EnvShieldException`'s message. See `BL-115` for the fix.
  - **`_kubernetes.py` — no `try`/`except` around `yaml.safe_load_all` at all**, so a malformed manifest raises the raw `yaml.YAMLError` uncaught rather than a wrapped message — already tracked as `BL-093`, not previously connected to this specific content-safety question. Confirmed here: fixing `BL-093` must reuse `_deployment.safe_yaml_error_message` (the same helper `BL-115` introduced), not `str(e)`, or it will reintroduce this exact leak the moment error handling is added. The two `EnvShieldException` sites that already exist in this file (multiple-containers / container-not-found) only echo container *names* (structural identifiers from the manifest's own `metadata.name`/`spec.containers[].name` fields) — not a concern of the same kind, left as-is.
  - **`_dotenv.py` — no parse-error path exists at all.** Dotenv format has no "fails to parse" case the way YAML/Python source does; its only `raise` is `FileNotFoundError` for a missing file. Trivially safe, nothing to fix.
- **Decision:** **Closed 2026-09-01.** All four parsers checked. One genuine leak found and fixed (`BL-115`); one pre-existing gap (`BL-093`) newly connected to this question with an explicit reuse instruction for whoever fixes it; two parsers confirmed safe by inspection, one of them (Python) with prior live reproduction. `BL-030`'s `_evaluate_source` is no longer blocked by this item.

### BL-115 — Docker Compose parser's YAML parse-error message echoed the offending line's raw content
Type: `SECURITY` · Evidence: `CONFIRMED` (live-reproduced, fixed, regression-tested) · Priority: **P0** (per this charter's own §4: "Any bug that can expose a secret is P0")
Source(s): `BL-031`'s parser-by-parser content-safety sweep, 2026-09-01 (Zeus dogfooding pass, investigating `BL-030`'s readiness — found incidentally while verifying an existing backlog item, not a Zeus-specific issue at all).
Component: `parsers/_docker_compose.py`, `parsers/_deployment.py` (new `safe_yaml_error_message`)

- **Problem:** `DockerComposeParser.get_vars`'s malformed-YAML handler built its `EnvShieldException` message from `str(e)` directly (`f"Could not parse '{file_path}': {e}. ..."`). `yaml.YAMLError.__str__()` (via its `problem_mark`/`context_mark` `Mark` objects) renders a code-context snippet that includes the actual offending line's text — by design, for human debugging, but exactly the class of leak this charter's §4 security invariants exist to prevent.
- **Generalization:** Not Zeus-specific — a property of PyYAML's own exception formatting, triggered by any malformed Compose file, on any project. Reproduced with a synthetic fixture, no Zeus file involved.
- **Reproduction:** A Compose file with `API_KEY: "AKIA-NOT-A-REAL-AWS-KEY_SECRET-PLACEHOLDER-VALUE` (unclosed quote, deliberately secret-shaped) on the malformed line. Before the fix, `str(e)` and therefore the raised `EnvShieldException`'s message contained `API_KEY: "AKIA-NOT-A-REAL-AWS-KEY_SEC ...` verbatim (truncated by PyYAML's own snippet renderer, but still a real, partial secret-value leak) — live-confirmed via direct `yaml.safe_load` before touching any EnvShield code, then re-confirmed through the actual `DockerComposeParser.get_vars` call path.
- **Fix:** New `parsers/_deployment.safe_yaml_error_message(e)` — builds a message from only `YAMLError`'s safe structural attributes (`.problem`/`.context` description strings, `.problem_mark.line`/`.column` as plain 1-indexed integers), never from `str(e)` or a `Mark` object's own `__str__`/`get_snippet()`, which is exactly what renders the leaking content. `_docker_compose.py` now calls this instead of interpolating `{e}` directly. Message quality is unaffected for a legitimate user — still names the failure type and exact line/column, just never the line's content.
- **Dependencies/relationships:** Found via `BL-031`; `BL-093` (Kubernetes parser has no error handling around its own YAML parse at all) must reuse this same helper when it's eventually fixed, or it will introduce this identical leak the moment a `try`/`except` is added there — noted explicitly in `BL-093`'s own entry.
- **Tests:** `test_docker_compose_parser.py::test_yaml_parse_error_never_echoes_the_offending_lines_content` — same secret-shaped fixture, asserts `"AKIA"`/`"SECRET"` are absent from the raised message while `"line"`/`"column"` are still present (message quality preserved). The pre-existing `test_parser_raises_clean_error_for_multi_document_yaml` (matches only on `"multiple YAML documents"`) is unaffected and still passes unmodified.
- **Verification:** Full suite 1045/1045 passed (was 1044; +1 new test), `ruff check .` clean. Live-reproduced both before (leak present) and after (leak absent) the fix, not assumed from the diff alone.
- **Decision:** **Fixed 2026-09-01, in the working tree — not yet committed, not yet released.** Given this charter's explicit "Any bug that can expose a secret is P0" rule, this is a release blocker once a release is next proposed (Part 0-equivalent severity), even though it was discovered and fixed outside of a release-prep pass.

### BL-050 — Large-repository `scan`/`undeclared` performance benchmark
Type: `RESEARCH` / `PERFORMANCE` · Evidence: `CONFIRMED` (real, profiled measurement against a real ~7,700-file monorepo — promoted from `NEEDS_EVIDENCE`, 2026-09-01)
Source(s): Zeus dogfooding pass, 2026-09-01. `envshield scan /home/rabbil/dev/zeus --json`, no config registered, read-only, no files written to Zeus.

- **Baseline (before this pass's fix), measured directly, not inherited from an earlier unlogged estimate:** repo-wide `scan` against Zeus (2,897 `.py` files; ~7,700 files total once other types are counted) — **22.1s wall time**, single-threaded, 99% CPU (`time` output: `21.91s user 0.10s system 99% cpu 22.118 total`), run twice for stability. This reproduces (and pins down the exact origin of) the "17–23s" figure `BL-113` had already cited informally from an earlier phase.
- **Profiled with `cProfile`** (against `_scan_files` directly, bypassing Rich output) to find the dominant cost, not guess at it. Result, ordered by cumulative time: **secret-pattern regex matching (`re.search`/`re.Pattern.search`/`re._compile`) accounted for roughly two-thirds of total time** — 25,859,312 `re.search` calls (25 patterns × ~1.03M scanned lines), because `SECRET_PATTERNS`' 25 patterns were stored and used as raw strings, forcing Python's `re` module to hash and cache-look-up each pattern string on every single call instead of matching against an already-compiled `Pattern` object. AST-based discovery (`discover_python_usages`, `ast.parse`, tree traversal) was, by contrast, cheap — about 8.7s cumulative out of the profiled ~51.6s total (profiling overhead inflates absolute numbers; the *proportions* are the finding). **This directly refutes an assumption worth naming explicitly: AST parsing is not the bottleneck. Regex-based secret scanning is.**
- **Fix (2026-09-01, this pass) — see `BL-114`.** After pre-compiling the 25 secret patterns once at module load instead of per-call: **17.1–17.3s**, measured three times for stability, a **~22% reduction**, with scan results confirmed byte-identical (`before == after` on the full `--json` output, diffed programmatically) before and after.
- **`scan --staged` measured separately, as explicitly requested — not merely inferred from the repo-wide number.** Using a disposable local clone of Zeus (never touching the real working tree or its git index — `git clone --no-local file:///.../zeus`, discarded after) with 3 realistic files staged: **0.22s.** Confirms `_collect_files_to_scan`'s staged-only path already does exactly what you'd want — it scans only the staged files, not the repository tree — so the hook-path cost (what a pre-commit hook or CI staged-check actually pays) is not the same problem as the repo-wide number above, and is not currently a bottleneck on a monorepo of this size. This answers the open question in the original entry (whether staged discovery can avoid repository-wide work): **yes, empirically confirmed.**
- **CPU utilization / multiprocessing headroom:** every measurement (before and after the fix) showed 99% single-core CPU, on a 12-core machine — the workload is CPU-bound and entirely single-threaded. Real headroom exists for a future embarrassingly-parallel-by-file optimization (each file's scan is independent), but this is a materially larger change (process orchestration, result-merging, Rich progress bar across workers) than this pass's scope — **not implemented, not designed further here**, recorded as the natural next performance step if repo-wide `scan` time becomes a real problem again after the regex fix.
- **Whether unchanged files are reparsed on every run:** yes, confirmed — there is still no caching (see `BL-052`, unchanged by this pass). But this pass's own profiling shows that matters less than it might seem: `ast.parse` itself was never the dominant cost (~1.7s of the profiled ~51.6s), so a caching layer would have saved much less than the regex fix already did. Caching remains a legitimate future direction, just not the highest-value one revealed by this pass.
- **Decision:** Baseline established and a real, evidenced, low-risk fix shipped in the same pass (`BL-114`). `BL-050` itself is now `CONFIRMED` rather than `NEEDS_EVIDENCE` and stays open only as the ongoing home for future large-repo benchmarking (e.g., if multiprocessing is ever pursued, re-benchmark against this same baseline).

### BL-114 — `scan`'s secret-pattern matching recompiled every regex on every call
Type: `PERFORMANCE` (fix) · Evidence: `CONFIRMED` (profiled, fixed, benchmarked, results verified unchanged) · Priority: P2
Source(s): Zeus dogfooding performance pass, 2026-09-01 — `BL-050`'s profiling of a real repo-wide `scan` against Zeus.
Component: `core/scanner.py` (`SECRET_PATTERNS`, `_scan_single_file`)

- **Problem:** `_scan_single_file`'s hot loop called `re.search(secret["pattern"], line)` for each of 25 secret patterns against every scanned line — `secret["pattern"]` is a raw string, so every one of the resulting ~25.8M calls (on Zeus) paid Python's `re` module's per-call pattern-string hash/cache-lookup cost, rather than matching directly against an already-compiled object.
- **Generalization:** Not Zeus-specific in any way — this is the secret scanner's own core loop, run identically on every `scan`/`scan --staged` invocation on any project. Zeus was simply large enough (~1M scanned lines) to make the cost visible and worth profiling; the underlying inefficiency exists on a five-file project too, just too small to notice.
- **Fix:** Added `_COMPILED_SECRET_PATTERNS`, a module-level `[(name, re.compile(pattern)) ...]` built once at import time from the existing `SECRET_PATTERNS`. `_scan_single_file` now iterates that list and calls `compiled_pattern.search(line)`. `SECRET_PATTERNS` itself — its existing `List[Dict[str, str]]` shape, with string patterns — is completely unchanged, since `importer.py` and several tests call `re.search(p["pattern"], ...)` against it directly; this fix is a purely internal, additive fast path for `scanner.py`'s own hot loop, not a change to any public data shape.
- **False-positive / regression risk:** None found. Same regexes, same flags, same match semantics, same first-match-wins `break` order — `re.compile(p).search(s)` and `re.search(p, s)` return equivalent match objects. Verified directly: full `--json` scan output against Zeus, before and after the fix, compared programmatically (`before == after`) — byte-identical (235 secrets, 217 undeclared variables, 9 skipped files, all identical).
- **Performance impact of the fix itself:** the point of the change — repo-wide `scan` against Zeus dropped from 22.1s to 17.1–17.3s (~22%), measured three times for stability.
- **Tests:** Full suite (1044/1044) unaffected by the change (no new test needed specifically for this — the existing `test_scanner_compliance.py`/`test_importer.py` suites already exercise `SECRET_PATTERNS` matching behavior directly against the untouched public list, and the before/after Zeus comparison is the regression evidence for the hot-path change itself).
- **Verification:** Full suite 1044/1044 passed, `ruff check .` clean, Zeus scan output byte-identical before/after.
- **Decision:** **Fixed 2026-09-01, in the working tree — not yet committed, not yet released.**
